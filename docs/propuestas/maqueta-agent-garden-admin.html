El Agent Garden es el backend

Vive en el API de HYPNIC (hypnic-platform, api.hypnic.us) como módulo src/garden/ con rutas /api/garden/*. Guarda plantillas, versiones, harness, MCP por agente, instancias, solicitudes, topes y auditoría, y está conectado con Google: crea, actualiza y borra los agentes en Agent Runtime, los registra en Agent Registry y les da identidad en IAM. El admin es un cliente más; el agente madre es otro. Nada de esto vive en el front ni se edita en la consola de Google.

Conexión con Google Agent Platform (antes Vertex AI Agent Builder)

conectado · proyecto hypnic-garden-01 · us-central1

El garden se conecta a las piezas de Google que antes se llamaban Vertex AI: Agent Garden (plantillas y ejemplos), Agent Runtime (donde corren), Agent Registry (inventario), Skill Registry (skills de Google) y Model Garden por Vertex (modelos). Habla con todas por adaptadores propios detrás del puerto RuntimeDeAgentes. Lo que se ve en la consola de Google es el reflejo de lo que el garden ordenó; nada hecho a mano en la consola cuenta como versión.

identidad de servicio del garden: garden-control@hypnic-garden-01.iam… · permisos: aiplatform.reasoningEngines.* · iam.serviceAccounts.create · cuota: 100 recursos por proyecto y región (pedido aumento a 300)

Lo que ya existe en el API y se reutiliza

  • apps.kind='agente' + agent_profile (agentes-data-house)
  • Bóveda y corredor de credenciales (POST /api/credenciales)
  • Techo y selección por consumidor del canal mcp (mcp-empresa-contrato, T1–T4)
  • MCPs de terceros (/api/admin/mcp-externos)
  • Consumo, créditos y 402 (POST /api/usage/events)
  • audit_log, memberships, áreas del Cerebro (migración 084)

Lo nuevo que el backend tiene que aprender

  • Plantilla, versión e instancia como entidades (garden_*)
  • Puerto RuntimeDeAgentes con dos adaptadores: Agent Runtime (ADK) y hypnic-agents
  • Harness y skills versionados en storage, resueltos al empaquetar
  • Clase de recurso MCP (empresa, comercio, cerebro, tercero, personal) y su candado por rol
  • Consumidor MCP por instancia (hoy es por desarrollo)
  • Solicitudes, topes por instancia y etiqueta de instancia en el gasto GCP

Reglas duras (viven en el backend, no en un prompt)

  • Ninguna ruta de solicitud ni del madre puede crear una plantilla estructural. CHECK en base de datos y 403 en el router.
  • Recursos de clase empresa (ERP, contabilidad, lago completo) solo seleccionables para rol madre o cerebro.
  • Escritura y gasto nacen apagados y exigen confirmación humana por llamada.
  • Un agente nunca lee storage ni Secret Manager por su cuenta: recibe archivos resueltos y credenciales por el corredor.
  • Nada editado en la consola de Google es versión. La versión es la fila de platform + el SHA del contenido.
  • Tope diario por instancia y mensual por empresa: al tope, pausa y aviso. Nunca «se nos crece por detrás».
